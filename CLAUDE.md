# CLAUDE.md — HackYeah 2026 / SmartCity (рабочее название: EventRoute)

Контекст для людей и для Claude Code. Читай целиком перед началом работы. Если что-то меняется в контрактах, правь этот файл в том же коммите.

## 1. Идея в одном абзаце

Участник регистрируется на событие (на демо: HackYeah, Tauron Arena, Краков) и указывает, откуда едет и к какому времени нужно быть на месте. Система планирует дорогу от события назад: поезд, затем городской транспорт и пешая часть до входа. Для каждого варианта считается вероятность успеть. Если поезд опаздывает, план пересчитывается и пользователь получает уведомление. Организатор и город видят агрегированную волну прибытий (сколько людей, когда и через какие узлы), чтобы управлять нагрузкой на транспорт.

Категория: SmartCity (мобильность, коммуникация с жителями, управление ресурсами, кризисное реагирование).

Покупку билетов делает пользователь: система даёт ссылку/кнопку на сайт перевозчика. Агент не платит и не вводит учётные данные.

## 2. Что мы показываем на демо (3 акта)

1. **Регистрация из Вроцлава** → три плана (самый надёжный / самый быстрый / самый дешёвый) с вероятностью успеть.
2. **Кнопка «поезд опоздал на 25 минут»** → мгновенное перепланирование, уведомление в Telegram.
3. **Экран города/организатора** → волна прибытий по часам и узлам, рекомендация (разнести слоты регистрации, усилить трамваи).

Строка для слайда: «Источник данных сейчас агент/парсер; в проде — партнёрский API. Покупает пользователь».

## 3. Архитектура

```
React (карта, таймлайн, дашборд)
        │  REST + SSE
FastAPI ── Planner (детерминированный, обратный расчёт от arrive_by)
        │      ├─ TrainProvider   (интерфейс)
        │      │     ├─ GeminiAgentProvider   (ищет на сайтах, строгий JSON)
        │      │     ├─ PlaywrightProvider    (запасной, фиксированные селекторы)
        │      │     └─ FixtureProvider       (записанные ответы, ВСЕГДА работает)
        │      ├─ LocalTransport  (граф остановок / GTFS Кракова, если доступен)
        │      └─ Reliability     (Монте-Карло, ~1000 прогонов)
        ├─ Validator (проверка всего, что вернул агент)
        ├─ City aggregates (синтетические участники → агрегаты)
        └─ Notifier (Telegram-бот)
```

Правила:
- LLM только оркестрирует и объясняет. Времена, маршруты и вероятности считает код.
- Любой результат агента проходит Validator, иначе используется Fixture.
- Планировщик не знает, откуда пришли поезда, он работает только с интерфейсом `TrainProvider`.

## 4. Контракты (источник правды)

### Общие правила
- Время: ISO 8601 с часовым поясом, `2026-10-04T09:21:00+02:00`. Время **без пояса модели отклоняют** (ошибка валидации), поэтому агент обязан возвращать пояс.
- Минуты: целые числа, поле с суффиксом `_min`. Деньги: злотые, суффикс `_pln`. Вероятность: от 0 до 1.
- Станции: полное польское название, как на Koleo (`Wrocław Główny`, `Kraków Główny`).
- Нет значения → `null`, поле не пропускаем.

### Event
```json
{
  "id": "ev_hackyeah2026",
  "name": "HackYeah 2026",
  "venue": "Tauron Arena Kraków",
  "venue_station": "Kraków Główny",
  "city": "Kraków",
  "start": "2026-10-04T10:00:00+02:00",
  "checkin_buffer_min": 30,
  "lat": 50.0675,
  "lon": 19.9917
}
```
`venue_target = start − checkin_buffer_min` — к этому времени нужно быть у входа.

### TrainOption
Один вариант междугородней поездки. Несмотря на название, это может быть и автобус (FlixBus из выдачи Koleo).
```json
{
  "id": "tr_001",
  "source": "koleo|fixture|playwright",
  "fetched_at": "2026-10-03T09:40:00+02:00",
  "mode": "train|bus",
  "category": "IC",
  "train": "IC 6100",
  "from": "Wrocław Główny",
  "to": "Kraków Główny",
  "dep": "2026-10-04T05:10:00+02:00",
  "arr": "2026-10-04T08:15:00+02:00",
  "price_pln": 64.0,
  "changes": 0,
  "delay_model": {"p_on_time": 0.7, "mean_delay_min": 6, "p95_delay_min": 25},
  "known_delay_min": 0,
  "url": "https://koleo.pl/rozklad-pkp/wroclaw-glowny/krakow-glowny/04-10-2026_04:00/all/all"
}
```
- `mode`: `train` для поездов, `bus` для FlixBus и других автобусов. Автобусы показываем, на фронте у них значок автобуса.
- `category`: категория из Koleo (`IC`, `TLK`, `EIP`, `REG`, `FLIX`, …).
- `train`: номер или название, если известен; иначе равен `category` (в выдаче Koleo номера нет).
- `price_pln`: может быть `null`, если цена неизвестна. Такой вариант показываем («цена на сайте»), но он не участвует в выборе `cheapest`.
- `delay_model`: Koleo его не даёт, заполняем по своей таблице для каждой `category`.
- `known_delay_min`: текущая известная задержка, обычно 0. При задержке плановое `arr` не меняем, меняется только это поле.
- `url`: ссылка на выдачу Koleo. Шаблон: `https://koleo.pl/rozklad-pkp/{откуда}/{куда}/{ДД-ММ-ГГГГ_ЧЧ:ММ}/all/all`.

### LocalLeg
```json
{
  "mode": "tram|walk|bus",
  "from": "Kraków Główny",
  "to": "Tauron Arena",
  "dep": "...", "arr": "...",
  "duration_min": 24,
  "std_min": 4,
  "line": "52"
}
```
- `dep`/`arr` — ожидаемые времена без задержек. `std_min` — разброс для Монте-Карло.
- `line`: номер линии; для `walk` равен `null`.
- `path: [[lat, lon], ...] | null` — точки маршрута участка по порядку, для линии на карте. Поле необязательное: в фикстуре его можно не указывать, в ответе API оно всегда есть (`null`, если точек нет). При `null` фронт рисует прямую между точками. Координаты проверяются: широта от −90 до 90, долгота от −180 до 180. Порядок именно `[lat, lon]`, как в Leaflet.

### Plan
```json
{
  "id": "pl_001",
  "labels": ["safest", "fastest"],
  "train": { "...TrainOption" },
  "local_legs": [ "...LocalLeg" ],
  "venue_target": "2026-10-04T09:30:00+02:00",
  "arrival_at_venue": "2026-10-04T08:50:00+02:00",
  "buffer_min": 40,
  "p_on_time": 0.93,
  "price_pln": 64.0,
  "overnight_stay": false,
  "explanation": "Короткое объяснение выбора (генерирует LLM по уже посчитанным данным)",
  "buy_url": "https://..."
}
```
- `labels` — в каких категориях план лучший: `safest`, `fastest`, `cheapest`. Один план может быть лучшим сразу в нескольких, тогда это **одна карточка с несколькими метками**. Поэтому в ответе от 1 до 3 планов.
- `venue_target` — когда нужно быть у входа (из Event).
- `arrival_at_venue` — ожидаемое прибытие ко входу с учётом `known_delay_min`.
- `buffer_min = venue_target − arrival_at_venue`. Может быть отрицательным (опаздываешь).
- `overnight_stay: true` — прибытие накануне, нужна ночёвка (см. раздел 5).

### CityOverview
```json
{
  "event_id": "ev_hackyeah2026",
  "participants_total": 420,
  "arrivals_by_slot": [
    {"slot": "2026-10-04T08:45:00+02:00", "count": 112}
  ],
  "nodes": [
    {"name": "Kraków Główny", "lat": 50.0677, "lon": 19.9479, "peak_count": 140,
     "peak_slot": "2026-10-04T09:15:00+02:00", "load": "low|medium|high"}
  ],
  "origins": [{"station": "Warszawa Centralna", "count": 150}],
  "recommendations": [
    {"type": "stagger_checkin|add_trams", "text": "Усилить трамвай 52 с 9:10 до 9:40", "severity": "low|medium|high"}
  ]
}
```
`arrivals_by_slot` — слоты по 15 минут (график волны прибытий).

### Эндпоинты
- `POST /api/plan` — вход: `{origin, event_id, arrive_by?, budget_pln?, mode_pref?}`, выход: `{request_id, plans: Plan[], status: "ok"|"no_options"}`.
  - `origin` — **станция** (полное название, как на Koleo). На фронте выбор из списка станций.
  - `arrive_by: null` → берём `venue_target` из события.
- `GET /api/plan/{request_id}/stream` — SSE-статусы поиска. События: `event: status` с `data: {"step": "search|found|local|reliability|done", "message": "Searching for trains…"}`, в конце `event: done` с `data: {"request_id": "..."}`.
- `POST /api/simulate/disruption` — вход: `{plan_id, train_delay_min}`, выход: `{affected_plan: Plan, plans: Plan[], notified: bool, message: str}`.
  - `affected_plan` — исходный план с задержкой (`train.known_delay_min`), для экрана «было / стало».
  - `plans` — пересчитанные планы. Альтернативы только с отправлением не раньше задержанного поезда (задержка известна в момент его отправления).
  - `notified: false` → уведомление не отправлено (нет Telegram), фронт показывает `message` сам.
- `GET /api/city/overview` — выход: `CityOverview`
- `GET /api/events/{id}` — выход: `Event`

## 5. Логика планировщика (коротко)

1. `venue_target = event_start − checkin_buffer`.
2. Локальный участок: время трамвая + пешком + запас по неопределённости → `station_deadline`.
3. Отбор поездов с `arr ≤ station_deadline`. Окно поиска начинается **с вечера предыдущего дня** (с 16:00 дня до события), а не только с утра события. Время события не меняется никогда: если подходящих поездов мало, ищем более ранние.
4. Надёжность: Монте-Карло по задержке поезда и длительности локального участка → `p_on_time`.
5. Выбор трёх планов: максимум `p_on_time`, минимум времени в пути, минимум цены.
   - Если один вариант побеждает в нескольких категориях, это один план с несколькими `labels` (одна карточка), а не дубли.
   - Если поезд прибывает **накануне дня события или ночью (до 06:00 в день события)**, план помечается `overnight_stay: true` («нужна ночёвка»).
   - Такие планы показываем, но они не могут быть `fastest` и `cheapest`, так как время в пути и цена без учёта ночёвки вводят в заблуждение. Они могут быть только `safest`, и только если в день события нет варианта с высоким `p_on_time`.
6. При задержке: пересчитать с новой `arr`, предложить альтернативу, отправить уведомление.

Пример (Koleo, проверено 2026-10-03): из Вроцлава к 9:30 у Tauron Arena в день события успевает несколько вариантов: IC 03:10 → 06:34, IC 05:10 → 08:15 и ночные FlixBus (01:46, 02:06, 03:51). Без ночёвки лучший по времени и надёжности — IC 05:10 → 08:15, он же `fastest`.

## 8. MVP-граница

**Must (без этого не питчим):** форма, три плана с вероятностью, перепланирование по кнопке, дашборд города на синтетике.
**Should:** живой Gemini-агент на одном маршруте, Telegram-уведомление, карта.
**Could:** реальный GTFS трамваев, несколько событий, мультиязычность.

Если на H12 живой агент не работает, не тратим на него больше времени: остаёмся на FixtureProvider и честно говорим об этом в питче.

## 9. Риски и запасные варианты

| Риск | Что делаем |
|---|---|
| Сайт блокирует / показывает капчу | Не обходим защиту. Переключаемся на Fixture |
| Агент возвращает мусор | Validator отбрасывает, повтор один раз, затем Fixture |
| Нет доступа к расписанию трамваев | Упрощённый граф остановок с 1–2 реальными маршрутами |
| Нет Wi-Fi на сцене | Всё демо работает на фикстурах локально, без внешних вызовов |
| Агент слишком долгий | Кэш заранее + SSE-статусы как фича |
| Не успели Telegram | Показываем уведомление в интерфейсе |

## 10. Правила разработки

- Mock-first: любая фича сначала работает на фикстурах, потом подключаем живой источник.
- Один формат данных (раздел 4). Меняешь контракт — сообщи остальным и обнови этот файл.
- Ветки: `main` + короткие ветки `d/…` (Backend), `f/…` (AI/Data), `a/…` (Frontend). Перед пушем `git pull --rebase`. Мержим часто, большие ветки не держим.
- Секреты только в `.env`, `.env` в `.gitignore`. Ключи API в репозиторий не коммитим.
- Агент никогда не вводит учётные данные и не платит. Покупка — только переход по ссылке пользователем.
- Персональные данные участников в демо синтетические. Реальные адреса и контакты не используем.
- Структура репозитория: `backend/`, `frontend/`, `data/fixtures/`, `docs/`.
